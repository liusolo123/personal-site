## 一、问题清单（按严重度）

### 🔴 P0-1 隐私风险：「朋友」分类照片仍提交在仓库中

`gallery.js` 只是在前端过滤掉了 `朋友` 分类（38 张，占全部照片一半以上），但 `photos/full/` 和 `photos/thumbnails/` 里的文件是真实存在的。一旦推送到公开的 GitHub 仓库，任何人拼出 `photos/full/photo_001.jpg` 这类路径就能直接访问——**前端隐藏 ≠ 隐私保护**。

处理方案（三选一）：
- **A（推荐）**：把朋友照片从仓库移除（保留本地原图），`photos.json` 中同步删除这些条目。仓库体积也从 47MB 降到约 25MB。
- B：仓库改为 private，用 Netlify/Cloudflare Pages 等支持私有源部署。
- C：`build-photos.py` 增加"仅导出非朋友分类"的开关，从源头不生成。

### 🔴 P0-2 `build-photos.py` 会覆盖手写的标题与分类

脚本按**扫描顺序**生成 `photo_001`、`photo_002`……并重写整个 `photos.json`。后果：
- 只要往 `D:\lr\out` 加一张排序靠前的新照片，**所有编号后移**，你手工标注的分类和标题会整体错位甚至被重置为"其他"。
- AGENTS.md 已经写了"不要随意重跑"，但这是用纪律规避缺陷，治标不治本。

修复方向（增量合并）：
1. 用 `original_name`（或内容 hash）作为稳定 key，而不是序号。
2. 重跑时先读入现有 `photos.json`，按 key 匹配，**保留已有的 `title`/`category`**，只为新照片生成默认值。
3. 删除源目录已不存在的条目（或保留并标记）。

### 🟡 P1-1 项目详情页全是占位符

`project.html` 的"展品详情 · 即将展出"占位区是 LOG.md 里挂着的头号待办。详情页框架（加载/错误/内容三态）已完成，只差内容。建议在 `projects.json` 中为每个项目扩展字段：

```json
{
  "id": "news-bot",
  "sections": [
    { "heading": "背景", "body": "..." },
    { "heading": "架构", "body": "...", "image": "projects/news-bot/arch.png" }
  ],
  "links": [{ "label": "GitHub", "url": "..." }]
}
```

渲染逻辑约 30 行，保持纯静态、数据驱动。

### 🟡 P1-2 转义不一致（XSS 隐患，当前数据下无实害）

`main.js` 渲染项目卡片用了 `escapeHTML`，但 `project.html` 内联脚本的 tags 渲染是裸拼 `innerHTML`（第 146-149 行）。数据都是自己写的所以没炸，但标准应统一。修法：把 tag 也用 `textContent` 或同款 `escapeHTML` 处理。

### 🟡 P1-3 未部署

`git remote -v` 为空，README 里写的 GitHub Pages 流程还没执行。部署前建议先完成 P0-1（朋友照片出库），否则隐私文件会永久留在 git 历史里（后删也要重写历史）。

## 二、优化建议（按优先级分层）

### 第一层：安全与正确性（建议本周内）
1. **朋友照片出库**（P0-1 方案 A），同步清理 `photos.json`。
2. **重写 `build-photos.py` 为增量合并模式**（P0-2），改完用现有 `D:\lr\out` 跑一次验证：重跑前后 `title`/`category` 不变。
3. 修掉 project.html 的转义不一致（P1-2，5 分钟的事）。

### 第二层：体验（1-2 周）
4. Lightbox：相邻预加载 + 加载占位动画 + 移动端左右滑动切换。
5. 页脚年份动态化；照片标题批量起一遍（75 张 → 出库后约 37 张，工作量可控）。
6. 补 OG meta（`og:title`/`og:description`/`og:image` 用一张代表作风光图）。
7. 关于我肖像补图（选一张自拍或用摄影作品代替，符合策展调性）。

### 第三层：性能与工程（照片量上去之后再做）
8. **WebP/AVIF 输出**：`build-photos.py` 里加一行 `img.save(path, "WEBP", quality=80)`，体积再降 30-50%，配 `<picture>` 回退。目前 37 张公开图约 25MB，暂不紧迫。
9. 画廊分页或"加载更多"：照片超过 100 张再考虑，现在 37 张一次渲染完全没问题。
10. 部署后的监控可选项：简单的访问统计（Umami/Plausible 等无 cookie 方案，一行 script）。

## 三、扩展方案（功能候选，按与策展主题的契合度排序）

### A. 内容向（最推荐，网站的价值在内容）

1. **项目详情填充** —— 把 4 个项目的真实内容写进去。尤其 `news-bot`（每日新闻早报）与你的 newsdigest 项目完全对应，可以写架构图、技术栈、效果截图；`personal-site` 本身也可以自我指涉地写一篇"本站是怎么做的"。
2. **新增展品** —— `finnews`（财经新闻去重系统）、ABBYY OCR 批处理工具等都可以作为新卡片，只需在 `projects.json` 加一条。
3. **数学笔记展区** —— 你是数学系，Obsidian 笔记系统是很好的差异化展品。可导出少量精选笔记为静态 HTML/MathJax 页面，挂在"造物"展厅下。
4. **策展日志 / 更新记录** —— 一个轻量的"本站大事记"时间线，比博客维护成本低，符合"策展"叙事。

### B. 摄影增强（发挥你的摄影内容优势）

5. **EXIF 展示** —— `build-photos.py` 用 Pillow 的 `getexif()` 提取焦距/光圈/快门/拍摄时间，写入 `photos.json`，Lightbox 里以小字展示。摄影站的质感立刻上来，且全自动零维护成本。
6. **拍摄时间线** —— 利用 EXIF 日期做按时间/季节的视图切换，与现有分类筛选并列。
7. **胶片编号叙事** —— 照片已有编号式命名，可在 Lightbox 计数器处强化"藏品编号"语言（如 `藏品 No.033 · 风光`）。

### C. 交互与功能

8. **画廊标题搜索框** —— 37 张照片时是锦上添花，数据驱动实现只需十几行。
9. **深浅主题切换** —— 目前是固定深色展馆风；可加一个"白盒子画廊"浅色模式（`variables.css` 已是全变量驱动，改造成本低于普通项目）。
10. **联系板块** —— 页脚或关于区加 GitHub / 邮箱入口。个人站最终要能"被联系到"。

### D. 部署与运维

11. **GitHub Pages 上线**（P0-3 之后）：仓库推送 → Settings → Pages。若想更稳，Cloudflare Pages 对静态站免费额度更大、国内访问相对友好。
12. **自定义域名**（可选）：`*.github.io` 换自己的域名，配合 CNAME 文件。
13. **sitemap.xml**：两个页面的站收益很小，可以放到最后。

## 四、建议实施顺序

```
第 1 步  朋友照片出库 + build-photos.py 增量合并 + 转义修复   ← 安全底线
第 2 步  推送 GitHub + 开 Pages，先让网站能被访问             ← 从 0 到 1
第 3 步  Lightbox 体验三连（预加载/加载态/滑动）+ 页脚年份 + OG
第 4 步  项目详情内容填充（先写 news-bot，素材最现成）
第 5 步  EXIF 提取 + 展示（一次脚本改造，永久受益）
第 6 步  肖像、数学笔记展区、主题切换…… 按兴趣挑
```

每一步都保持现有原则：**纯静态、数据驱动、小步提交**。这个项目最难得的地方是架构干净（零依赖、CSS 全变量、数据与渲染分离），扩展时不要破坏这一点。
